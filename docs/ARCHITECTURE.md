# Базовая архитектура

## Статус решений

Архитектурные границы и стек утверждены. Версии зависимостей будут зафиксированы только при создании workspace, чтобы не записывать устаревшие номера заранее.

## Утверждённый стек

- Monorepo на TypeScript с `pnpm workspaces`.
- Клиент: Vite, React для меню/HUD и императивный Three.js runtime для игрового кадра.
- Коллизии: Rapier 3D/WASM как инструмент запросов к миру; игровое движение реализуется собственным кинематическим контроллером.
- Backend: Node.js и Fastify как модульный монолит.
- Данные: PostgreSQL; Redis и очередь задач добавляются только при появлении измеренной потребности.
- Контент: glTF/GLB для визуальной геометрии, отдельная упрощённая collision mesh и версионированный manifest карты.
- Хранилище тяжёлых файлов: S3-совместимое object storage и CDN.
- Основная цель производительности и совместимости MVP: актуальный desktop Google Chrome.

Почему не готовый rigid-body controller: для bunnyhop и surf нужны управляемые формулы ускорения, трения и clipping скорости по нормали поверхности. Rapier прямо предупреждает, что управление персонажем обычно специфично для конкретной игры; его shape-cast/collision-возможности полезны, но правила движения должны принадлежать проекту.

Требования и метод проверки близости к CS2 вынесены в `docs/MOVEMENT_FIDELITY.md`. Значения physics constants не угадываются и не копируются из Source 1 как будто это CS2: они фиксируются после измерения выбранного эталонного CS2-сервера.

## Границы приложений

### `apps/client`

- **Web shell:** загрузка, главное меню, выбор карты, инвентарь, кейсы, настройки.
- **Game runtime:** scene, camera, render loop, input, audio, map lifecycle.
- **HUD:** скорость, таймер, чекпоинт, подсказки, пауза.
- **Local session:** текущая попытка, рестарт, запись input frames и ghost.
- **Network:** загрузка manifest, профиль, отправка результата и получение статуса проверки.

React не должен обновлять состояние на каждом игровом кадре. Высокочастотное состояние хранится внутри runtime; в UI передаются только редкие снимки состояния.

### `apps/api`

Один развёртываемый backend с изолированными доменными модулями:

- identity и сессии;
- профили и настройки;
- каталог и версии карт;
- приём результатов;
- таблицы лидеров;
- кошелёк и ledger;
- кейсы и drop tables;
- демонстрационное пополнение валюты;
- инвентарь и loadout;
- административная публикация контента.

Микросервисы на старте не нужны. Границы модулей и transactional outbox позволят отделить сервис позже, если появится реальная нагрузка.

### `apps/run-verifier`

Фоновый процесс получает попытку, повторяет input replay на канонической версии движения и карты, проверяет чекпоинты и ограничения, затем принимает или отклоняет результат. Он импортирует тот же `packages/movement`, что и клиент, но не доверяет вычисленным клиентом времени, скорости или награде.

## Общие пакеты

### `packages/movement`

Единственный источник правил движения:

- фиксированный simulation timestep;
- ground/air acceleration и friction;
- wish direction и ограничение wish speed;
- gravity, jump buffer и режим auto-bhop;
- sweep/slide и clipping скорости по normal;
- определение ground, slope и surf surface;
- параметры пресетов движения;
- сериализация минимального состояния для replay и проверки.

В MVP прыжок автоматически выполняется на первом допустимом simulation tick, пока действие `jump` удерживается. Отдельного manual-bhop leaderboard не будет.

Пакет не должен зависеть от React, DOM, UI или backend-фреймворка.

### `packages/game-protocol`

Версионированные схемы API, ошибок, replay payload и событий. Клиент и сервер генерируют типы из одних схем; входные данные валидируются во время выполнения.

### `packages/map-format`

Manifest карты описывает:

- `mapId`, `version`, checksum и required movement preset;
- spawn, finish и kill zones;
- упорядоченные или разветвлённые checkpoints;
- режим карты: training, bhop, surf или mixed;
- difficulty и par time;
- ссылки на visual mesh, collision mesh, lightmap и audio;
- допустимые assists и правила наград.

Визуальная геометрия никогда не считается источником серверной коллизии. Публикация карты создаёт неизменяемую версию с checksum.

### `packages/ui`

Токены, доступные компоненты меню, модальных окон, карточек карт, инвентаря и HUD. Визуальное направление: тёмная спокойная основа, ясная типографика, сдержанные неоновые акценты и отдельный наградной цвет. Интерфейс не повторяет HUD или визуальный язык CS2.

## Игровой цикл одного кадра симуляции

1. Считать нормализованный input для текущего fixed tick.
2. Вычислить направление желания игрока относительно yaw камеры.
3. Применить ground friction либо air acceleration.
4. Обработать jump buffer/auto-bhop и gravity.
5. Выполнить capsule sweep по предполагаемому перемещению.
6. Разрешить столкновения, несколько раз clip-нуть velocity по normal.
7. Определить ground/surf state и события зон.
8. Записать компактный input frame и контрольный state hash.
9. Интерполировать только отображение между simulation states.

Физика не использует переменный `delta time` рендера. Параметры движения хранятся в версионированном preset: изменение значений не меняет старые таблицы лидеров и повторы.

## Поток прохождения

1. Клиент получает manifest и конкретную версию карты.
2. Карта и WASM-runtime загружаются до старта таймера.
3. Клиент записывает input frames, события checkpoints и локальный ghost.
4. После финиша API создаёт попытку со статусом `pending`.
5. Verifier воспроизводит попытку на нужной версии карты и movement preset.
6. При успехе одна транзакция принимает результат, обновляет лучший результат и начисляет награду через ledger.
7. Клиент получает итог `accepted` или понятную причину `rejected`.

## Поток открытия кейса

1. Клиент отправляет только идентификатор кейса и idempotency key.
2. Сервер внутри транзакции проверяет цену и блокирует кошелёк.
3. Цена списывается записью ledger, а не прямым изменением баланса без истории.
4. Сервер выбирает результат по опубликованной таблице выпадения и сохраняет доказуемую запись открытия.
5. Предмет добавляется в инвентарь; транзакция фиксируется целиком.
6. Клиент анимирует уже определённый сервером результат.

Повтор запроса с тем же ключом возвращает тот же результат и не списывает валюту снова.

## Поток демонстрационного пополнения

1. Клиент показывает только заранее заданные пакеты тестовой валюты и постоянную маркировку «Демо — деньги не списываются».
2. Клиент не запрашивает номер карты, банковские данные, адрес плательщика или подтверждение настоящего платежа.
3. `POST /demo/top-ups` принимает package id и idempotency key.
4. Backend проверяет demo feature flag и создаёт запись ledger с причиной `demo_top_up`.
5. Повторный запрос возвращает прежнюю операцию без повторного начисления.
6. В production feature flag должен быть выключен, если окружение перестаёт быть демонстрационным.

Платёжный SDK, webhook и сущность настоящего платежа на этом этапе отсутствуют. Demo-flow тестирует интерфейс и бухгалтерию виртуальной валюты, а не имитирует обработку реальной банковской операции.

## Основные данные

- `users`, `sessions`, `profiles`, `settings`;
- `maps`, `map_versions`, `movement_presets`;
- `runs`, `run_checkpoints`, `replays`;
- `wallets`, `wallet_ledger`;
- `cosmetic_items`, `inventory_items`, `loadouts`;
- `cases`, `case_versions`, `case_drop_entries`, `case_openings`;
- `outbox_events`, `audit_log`.

Таблицы лидеров лучше строить из принятых runs и кешировать, а не считать отдельным источником истины.

## API первого релиза

- `POST /sessions/guest` — гостевая сессия;
- `GET /me` — профиль, баланс и loadout;
- `GET /maps` и `GET /maps/:id/versions/:version` — каталог и manifest;
- `POST /runs` — отправка попытки;
- `GET /runs/:id` — статус проверки;
- `GET /leaderboards/:mapId` — результаты с фильтром movement preset/assists;
- `GET /inventory` и `PUT /loadout` — косметика;
- `GET /cases` и `POST /cases/:id/openings` — каталог и открытие.
- `GET /demo/top-up-packages` и `POST /demo/top-ups` — только демонстрационное начисление.

Это контрактный набросок, а не уже созданный API.

## Надёжность и защита

- Браузер считается недоверенной средой.
- Баланс, drop result, награда и accepted time определяет только backend.
- Replay ограничивается по размеру, частоте и длительности.
- Run привязан к map version, movement preset и версии verifier.
- Экономические операции используют транзакции, idempotency и audit trail.
- Demo top-up защищён feature flag, rate limit и отдельной причиной в ledger; его нельзя перепутать с реальным платежом.
- Авторизация, rate limiting, CSRF/CORS и security headers проверяются до публичного релиза.
- Секреты, административные методы и приватные asset origins не попадают в клиентский bundle.

## Тестовая стратегия

- Unit: формулы ускорения, friction, clipping, jump и расчёт награды.
- Golden replay: сохранённый input обязан приводить к ожидаемому времени и state hashes.
- Property tests: отсутствие NaN, прохода сквозь стену и отрицательного кошелька.
- Integration: транзакция открытия кейса и принятия run.
- E2E: от входа до прохождения карты, начисления и экипировки предмета.
- Performance: CPU frame budget, draw calls, размер карты, время загрузки и память.

## Развёртывание

Для первого публичного теста достаточно CDN для клиента/контента, одного API-процесса, одного verifier worker и managed PostgreSQL. Redis, autoscaling и разделение сервисов добавляются после измерения очереди проверок и нагрузки.

## ADR, которые нужно принять перед кодом

1. Fixed tick, единицы мира и первый измеренный movement preset.
2. Формат карты и пайплайн Blender → опубликованная версия.
3. Модель гостевой учётной записи и последующей привязки.
4. Точный профиль CS2 bhop/surf-сервера для эталонных замеров.
